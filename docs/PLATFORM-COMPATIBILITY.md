# Marketplace and wallet compatibility status

**Status: standards-oriented and locally verified; not certified by Ebisu's Bay or every wallet/marketplace.** A smart contract cannot compel third-party indexers to discover a collection, parse a particular URI scheme, render SVG identically, refresh cached metadata, or show the NFT in every wallet UI.

## Compatibility hardening in the current build

- `UltraCat5212` exposes standard ERC-721 ownership, approval, transfer, name, symbol, and metadata behavior through ERC721A. Tests check ERC-165 (`0x01ffc9a7`), ERC-721 (`0x80ac58cd`), ERC-721 Metadata (`0x5b5e139f`), and ERC-2981 (`0x2a55205a`).
- `tokenURI(tokenId)` is available for every minted token and returns Base64-encoded JSON with `name`, `description`, `image`, and `attributes`. `image` is a Base64 data URI containing self-contained SVG.
- Each NFT SVG is a square **512×512** document drawn on a 64×64 crisp pixel grid. It has inline vector shapes/colors and no scripts, external images, linked stylesheets, or remote fonts.
- `contractURI()` returns collection-level name, description, on-chain logo image, and royalty fields. Token and collection image data are generated by the immutable renderer contract.
- Local VM tests deploy both contracts, decode token JSON and nested SVG, validate interface IDs, and check royalty reports. A full local sweep called `tokenURI()` for all 5,212 token IDs: all 5,212 JSON records and nested SVGs parsed, every SVG was 512×512 and byte-distinct, and the maximum measured token-URI call was 798,917 local-VM gas. The report is `release/all-art-validation.json`. A separate XML-parser check also parsed all 33 preview-gallery SVGs and the `contractURI()` collection logo. These checks validate generated output, **not** any third-party display pipeline. `release/collection-logo.svg` is a convenience copy of the on-chain logo for inspection; the contract remains canonical.

## What the platform documentation does and does not establish

- The [ERC-721 specification](https://eips.ethereum.org/EIPS/eip-721) defines `tokenURI` as the optional metadata interface; consumers still choose how to fetch and display it.
- [OpenSea's current metadata-storage guide](https://docs.opensea.io/docs/metadata-storage) explicitly lists `data:application/json;base64,...` as an on-chain metadata URI for small/generative collections. That supports the chosen URI format on OpenSea's documented path, but it does not certify OpenSea on Cronos or other marketplaces.
- [OpenSea contract-level metadata](https://docs.opensea.io/docs/contract-level-metadata) documents collection-level JSON and the `contractURI()` hook. The contract supplies that hook and an embedded logo.
- Ebisu's Bay supports Cronos collections ([site](https://app.ebisusbay.com/)) and publishes a [GET `/nft` API reference](https://ebisusbay.readme.io/reference/get_nft.md). That reference documents `collection` and `tokenId` lookup plus generic `image`, `image_data`, and `original_image` response fields, but does **not** specify whether its indexer accepts `data:application/json;base64` or renders nested `data:image/svg+xml;base64`. I ran the documented API query against Wolfies #1 as a control: it returned HTTP 200, six attributes, and a CDN/proxied HTTPS image. The sandbox could not fetch that returned CDN image URL, so this validates the API query shape only—not Ebisu's image rendering or support/lack of support for embedded SVG. ULTRA CAT has **not** been indexed or tested there, so this must not be described as confirmed until an exact-format test succeeds.
- MetaMask's current help page lists NFT auto-detection networks as Ethereum, Base, Linea, SEI, Monad, and Avalanche—not Cronos—and says users can manually import ERC-721/1155 NFTs on any network. It also cautions that not all NFTs may display correctly from third-party metadata sources. See [MetaMask's wallet NFT guidance](https://support.metamask.io/manage-crypto/nfts/nft-tokens-in-your-metamask-wallet/). Its separate `wallet_watchAsset` NFT flow is documented as experimental and extension-only ([developer guide](https://docs.metamask.io/metamask-connect/evm/guides/metamask-exclusive/display-tokens/)). So Cronos wallet discovery and artwork display still cannot be promised automatically.

Before deployment, use [`EBISUS-BAY-PREDEPLOY-COMPATIBILITY.md`](EBISUS-BAY-PREDEPLOY-COMPATIBILITY.md) to run the no-contact public-API/UI probe. The marketplace advertises Cronos support, but the format itself has not been confirmed there; if the probe cannot be indexed, the public docs are insufficient to remove the uncertainty. The final renderer is immutable after deployment.

## Required post-deployment compatibility checks

1. On Cronos mainnet, call `supportsInterface`, `ownerOf`, `tokenURI`, `contractURI`, and `royaltyInfo` through a public RPC and an independent explorer. Decode several token URIs and verify the JSON, SVG, dimensions, and attributes match `release/trait-manifest.json`.
2. After the NFT contract is visible to Ebisu's Bay's indexer, run `node scripts/check_ebisus_api.js <contract-address> <tokenId>` against the documented `/nft` API and inspect the actual item page. Test normal, rare, 1/1, and reserve-owned examples (including #1, #133, #631, #701, #702, and #5,212). Verify image, trait display, ownership, transfers, and royalty fields. If the collection/API page is absent, treat that as unverified—not proof of image-format rejection—and decide whether to request indexing or pause.
3. Check the actual wallets used by holders on Cronos (including Crypto.com DeFi Wallet and MetaMask where applicable). Verify chain/network selection and manually add/view a token where the wallet requires it. A wallet UI's collection discovery is separate from ERC-721 transferability.
4. Test gallery/rendering on desktop and mobile browsers and check marketplace thumbnails after indexing; a platform may cache a converted image or render SVG differently.

The canonical art and metadata remain queryable from the Cronos contracts even if a particular UI fails to display them. If a marketplace or wallet does not support embedded data-URI SVG, a hosted or mirrored image/API might improve that platform's compatibility, but it would add an external presentation layer and must be separately approved; it is not part of this fully on-chain build.
