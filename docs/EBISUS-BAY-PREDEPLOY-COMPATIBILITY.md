# Ebisu's Bay pre-deployment compatibility gate

**Do not deploy the final collection until an exact-format check succeeds, or the owner explicitly changes the risk requirement.** The collection's `tokenURI` and renderer addresses are immutable after deployment. Its intended output is fully on-chain, but no contract can force a marketplace to decode or render it.

Ebisu's Bay supports Cronos collections and publishes an API reference for `GET /nft`, but that reference documents generic `image`, `image_data`, and `original_image` fields—not the URI schemes its indexer accepts. A live response for an existing Wolfies NFT uses a CDN/proxied HTTPS image; that does not prove either support or lack of support for embedded SVG. See the [marketplace](https://app.ebisusbay.com/), its [NFT API reference](https://ebisusbay.readme.io/reference/get_nft.md), and the broader [platform compatibility note](PLATFORM-COMPATIBILITY.md).

## No-contact public-API probe (preferred first check)

If the owner does not want to contact Ebisu's Bay leadership, its published read-only API can still be used for an empirical check:

1. The test-only contract source is `probe/UltraCatCompatProbe.sol`; run `npm run test:probe` to compile it and locally validate its nested Base64 JSON/SVG output. This local test passed, but it does not test Ebisu.
2. Follow `docs/PROBE-SIGNING-GUIDE.md` and open `probe/deploy-probe.html` from a local server in your own browser. The helper accepts only the reviewed renderer and probe bytecode hashes, checks Cronos Mainnet and the selected treasury, and submits transactions only after you explicitly approve them in your wallet. It deploys the shared renderer once, then the separate one-token probe with constructor arguments `(recipient, rendererAddress, royaltyReceiver)`. The probe mints only one clearly named test token to the selected treasury; it does not touch production ULTRA CAT tokens. If the probe passes, reuse that exact renderer address for the final collection. This is an irreversible mainnet deployment; you sign and pay. Never share a seed phrase or private key.
3. After Ebisu has had time to index it, run `node scripts/check_ebisus_api.js <probe-contract> 1`. The script calls Ebisu's documented `/nft?collection=...&tokenId=...` endpoint and checks returned metadata/image fields. Also open the probe token's actual Ebisu's Bay item page and verify both the thumbnail and detail image render; an API record alone is insufficient.
4. If desired, manually import the probe NFT into MetaMask on Cronos Mainnet and verify it there; test Crypto.com DeFi Wallet too if it is a target client. These checks cover only the clients tested and do not guarantee universal rendering.
5. Proceed to the production contract only after the API and actual Ebisu item UI show the expected image, and after the owner accepts the remaining per-platform risk. A missing API response means “not yet verified” (possibly not indexed), not necessarily “unsupported.” If the API or UI is inconclusive, do not deploy the final collection; use the optional regular technical-support request below or stop.

This probe is an empirical Ebisu check, not a guarantee for every wallet or marketplace, nor a guarantee that Ebisu's indexer will handle every token's metadata identically. The exact public API response schema is generic and does not promise data-URI support. The owner must decide whether those remaining limits are acceptable before main deployment.

## Copy/paste support request (optional if the public probe is inconclusive)

**Subject:** Pre-deployment check: Cronos ERC-721 with on-chain Base64 JSON and SVG metadata

Hello Ebisu's Bay team,

We are preparing **ULTRA CAT**, a 5,212-item ERC-721 collection for Cronos Mainnet (chain ID 25). Before deploying the immutable collection, could your technical team confirm whether your indexer and listing UI support this exact metadata format?

- `tokenURI(tokenId)` returns `data:application/json;base64,<...>`.
- The decoded JSON contains standard `name`, `description`, `image`, and `attributes` fields.
- `image` is `data:image/svg+xml;base64,<...>`; it decodes to a self-contained 512×512 SVG on a 64×64 crisp pixel grid, with no scripts, external images, fonts, or stylesheets.
- `contractURI()` returns Base64 JSON with a Base64 SVG collection image and ERC-2981-style royalty fields (`seller_fee_basis_points: 500`, `fee_recipient: <treasury>`).
- The contract implements ERC-721, ERC-721 Metadata, ERC-165, and ERC-2981 interface support; token art and metadata are generated by an immutable renderer contract.

Could you please confirm:

1. Does the collection indexer decode a `data:application/json;base64,...` value returned by `tokenURI()` on Cronos Mainnet?
2. Does the image pipeline decode the nested `data:image/svg+xml;base64,...` image and render SVG thumbnails/details pages?
3. Does your collection profile use `contractURI()`? If so, does it accept an embedded data-URI collection logo?
4. Does the marketplace read ERC-2981 royalties, and is there a collection registration, allowlisting, or manual metadata-refresh step?
5. Can we test the exact response format on a supported test contract or testnet before deploying the final immutable collection?
6. If any element is unsupported, what exact URI/image format do you require? We intend to keep all NFT art and metadata on-chain, so please distinguish required formats from optional hosted fallbacks.

We can provide the Solidity sources, sample decoded JSON/SVG, and a deployed test address if needed. Please do not treat the collection as ready for public sale until we have confirmed image rendering and collection indexing.

Thank you.

## After an answer

- Save the support response alongside the release package.
- If the exact on-chain format is supported, deploy only after the owner has reviewed the final artifacts and treasury control. After indexing, test ordinary, rare, 1/1, and reserve-owned tokens, including IDs **1, 133, 631, 701, 702, and 5,212**.
- If it is not supported, stop and decide explicitly whether to (a) keep the fully on-chain design and accept that some marketplace UIs will not display it, or (b) approve a different presentation layer/new contract design. Do not silently replace on-chain media with hosted metadata.
